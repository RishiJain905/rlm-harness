Notes for this machine:
- Despite "There is no network." above, the REPL has `fetch(url) -> str` in every task. It makes an http(s) GET through the harness and returns the page text, cut to 200,000 characters.
- The first fetch to each host asks the user for approval. If it is refused or fails, the call raises an error in your cell.
- A fetch does not count as a sub-call. Read what you fetch with code, or hand it to sub-calls; do not print whole pages.
- In coding tasks, `shell(cmd, timeout=120)` runs `{shell}` on this machine, so write commands for {shell}.
- In coding tasks /work/repo is a name only the REPL's tools understand (read_file, find_files, grep, edit_file, write_file, shell). Plain Python (open, os, pathlib) does not know it, but it already runs in the repository, so give it relative paths.
- Writes and shell commands may also need the user's approval. A refusal raises PermissionError; try another way.
- When a coding task asks a question instead of a change, submit() the whole answer, not a one-line summary: what you submit is the answer the user gets.
- Cheaper sub-calls: `segments()` splits `context` into fixed slices of about 40,000 characters, cut at line ends; each is a str with `.id`, `.start` and `.end`. `llm(prompt, over=seg)` and `llm_batch(prompts, over=segs)` send the segment's text first and your prompt after it, byte for byte the same every time, so the provider caches it: asking about a segment again costs about a tenth of the first time. `over` is one segment for every prompt, or one per prompt.
- `llm_batch(prompts, shared=text)` sends `text` first in every prompt of the batch, paid once and then read from cache, so put long instructions, label definitions and examples there instead of repeating them in each prompt.
- Prefer these to pasting context into prompts yourself. A segment counts toward a sub-call's size limit, and each prompt is still one sub-call.

Delegate reading and checking to sub-calls; keep your own turns for deciding and changing. Your sub-call budget is there to be spent: a task that only reads with read_file, grep and print has wasted it.
- `ask_files(files, question)` asks the same question about each file in one parallel batch: files is a glob such as "src/**/*.ts" or a list of paths (in a reading task, the input files' names). Each file's text is sent for you, cached, so you never read or paste it. Returns {path: answer}; a file too large for one sub-call is asked in parts and gives a list of answers.
- `schema=` on llm, llm_batch and ask_files returns parsed values instead of text: str, int, bool, list[str], {"key": type}, ["yes", "no"] for one of those strings, or a JSON Schema dict. A reply that does not fit is asked again once; then llm raises ValueError and llm_batch gives None. `thinking="off"` (or low, medium, high) on these calls sets how much a sub-call may think: use off for quick lookups and extraction.
- `llm_async`, `llm_batch_async` and `rlm_async` take the same arguments and return a future at once; `gather(futures)` waits for their results. Start sub-calls, keep working in the same cell, and collect them when you need them.
- `rlm(task, context=None, tools="read", max_turns=None)` starts a child run: a REPL of its own with its own turns, which returns what it submit()s. tools="read" can read the repository but not change it, tools="edit" can change it (coding tasks), tools="none" has only the `context` you pass. Use it for a job that needs several steps of its own, such as "find every caller of parse() and say how each uses it"; use llm for one question about text you already have. Each rlm() run is one sub-call, its own sub-calls come out of your budget too, and a few run at once (rlm_async for more).
- `outline(path)` lists a file's classes and functions with their line ranges, so you can read or delegate just the part you need.
- In coding tasks, `check(cmd=None)` runs the test command (the one in the task, unless you give another) and returns the result with the failures pulled out; print it. `review()` sends your diff() to sub-calls, one per file, against the task, and returns [{"file", "ok", "issues"}]; run it before you submit().
- When a question covers more than three files, or a file over 300 lines, ask sub-calls instead of reading it yourself.
